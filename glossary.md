# Glessner glossary

These are the names for the parts of Glessner, on screen and in the data. Use them in issues, code comments, commit messages, and documents, so that each name means one thing. If something new needs a name, add it here first.

## Screen layout

```text
+------------------------------------------------------------------------------+
| CASE PANEL: case name and state, path (Overview, Timeline, To investigate,   |
|             Findings, Audit trail), search, Case menu, status line           |
+------------------------------------------------------------------------------+
| HOSTS PANEL (Hosts, in the Case menu)                                        |
+----------------------+------------------------------------------+------------+
| SOURCES PANEL or     | TIMELINE PANEL                           | LEGEND     |
| VIEW FILTER (1 open) | Timeline toolbar, then the state line    | (Legend    |
|                      | time axis (UTC), then any zone axes      | button     |
|                      +---------------+--------------------------+ or L)      |
|                      | lane labels   | timeline canvas:         |            |
|                      |               |   density bars, ticks,   |            |
|                      |               |   logon arrows, links    |            |
+----------------------+---------------+--------------------------+------------+
| DIVIDER (drag to resize)                                                     |
+------------------------------------------------------------------------------+
| DETAILS PANEL: Event page, pile list, To investigate page, Suggestions page, |
|                Rules page, Import page, Findings page, or Audit trail        |
+------------------------------------------------------------------------------+
```

While the path's Overview step is current, the **Case overview** covers everything under the Case panel and the Hosts panel; the timeline stays loaded behind it.

Three words describe parts of the screen, and each has one meaning:

- A **panel** is a top-level area of the layout: the Case panel, the Hosts panel, the Sources panel, the View panel, the Timeline panel, the Legend, and the Details panel.
- A **page** is one of the things the Details panel shows, one at a time, such as the Event page or the Rules page. The Case overview is the one page that covers the panels instead.
- A **menu** opens on a right-click, or from a menu button, as the Case menu does.

Avoid "window", "pane", "tile", and "section" for parts of the app. "Window" means a span of time.

## Panels and their parts

| Name | What it is |
|---|---|
| Case panel | The strip across the top, grouped by job: the case name with its **case state** under it (open, or closed and when; whether the evidence still matches intake, a problem any check found staying until a full re-hash matches; and the analyst), the **path**, the search box and its Search help button (?), the **Case menu**, and the status line. |
| Path | The Case panel's five steps in the triage order: **Overview**, **Timeline**, **To investigate** (with its counts), **Findings**, which opens the Findings page, and **Audit trail**. The current step is outlined. It follows the Details panel: To investigate's page, the Findings page, and the Audit trail page light their steps, and any other page lights Timeline; the Timeline step takes the panel off those pages, to the event in focus or the opening hint. |
| Case menu | The Case panel's **Case ▾** menu button, holding the setup and record work: Hosts, Tools, Import, Rules, Export, Audit trail, and Cases. Its button carries the Hosts and Rules counts while it's closed. A click, Enter, or Space opens it, the arrow keys, Home, and End move in it, Escape closes it and gives the focus back to the button, and Tab, a click elsewhere, or the focus leaving it closes it. |
| Case overview | The page a case with events opens on, other than on a reload, which comes back to the page shown (a new or empty case opens on the Tools page), and the path's Overview step: **Start here**'s leads; **Your progress** (marks by verdict, leads worked, suggestions decided and pending, marked events sharing a logon session, file, or source IP with unreviewed events, notes, your last action, and a By host table); **What the case holds** per host, with "and K skipped" under a host's event count for the rows its latest tool runs read and made no event of; **Gaps** (runs that failed or loaded nothing, files intake couldn't identify or read, folders it couldn't list, log clears, hosts without event logs); and **Integrity** (the evidence hashed at intake, any change found since, the last full re-hash, `manifest.jsonl` against its record in the journal (with a warning when it grew past or differs from that record, or is missing), the journal's entries, which times the page shows, and the build). It covers the panels; the timeline loads behind it once it shows. A number that stands for events opens them: on the timeline through the View, or on To investigate or the audit trail. |
| Lead | One of the Case overview's places to start, from tool output, rules, and clock checks only, never a model: a cluster of alerts per host and tool (Hayabusa hits at medium level or above, Suricata alerts at severity 1 or 2, imported fast alerts at priority 1 or 2), split where two are more than 30 minutes apart; a suggestion rule's suggestions; or a host clock measured against a capture. Ranked by severity (critical, high, medium, rules, clocks), then the earliest time. An alert lead's chips name the tool's version and the rule sets of the runs that made its alerts, and read "Hayabusa rules not recorded" for a Hayabusa run made before case format 4. **Worked** when each of its events has a mark or a decision, or for a clock, when it's aligned. Each has one action: Open on timeline, Review suggestions, or Show in Hosts; Open on timeline says how many of the lead's events the Sources or the View hide. |
| Timeline toolbar | The row at the top of the Timeline panel, in the **Timeline band**, a tinted strip headed "Timeline" that the Sources, View, and Legend panels' heads share: the Lanes selector, Fit case, Sources, View, the toggles, the **Times switch** when a host's clock was measured against a capture, + zone, and Legend. Each control, and each of the Case panel's, has a one-line hover hint saying what it does. |
| State line | The line under the Timeline toolbar, always in view: "Showing X of Y events on the timeline", the one total, X being the events the Sources and View show over the whole case and Y the case's events on the timeline; "In this window: N", the events in the window drawn ("…" until that window's data answers); a pill for each hidden category, Hidden by Sources, Hidden by the View, and machine accounts' logon links, each naming what it hides, counting its own, and with a Show that clears that one alone; the clock the times are on, with Align or Show recorded; and the window, start to end in UTC with its span. |
| Legend | The panel right of the Timeline panel that the Legend button or L opens: every mark the timeline draws, ticks by mark, the hollow suggestion, the red box, the selection's box, the yellow fill, the faded gray tick, density shades and their red top edge, logon arrows, window links, the clock pair link, and the lane label flags, in the page's own colors, dark mode's included. It draws nothing on the timeline. This browser remembers whether it's open. |
| Lanes selector | The drop-down that picks the lane keys, such as Mark > Role > Host |
| Toggles | The Logon links and Hide machine accounts checkboxes in the Timeline toolbar. With Logon links off, the server doesn't read the window's links at all. Hide machine accounts leaves out the logon links of accounts ending in $, not their events. |
| Control counts | Sources and View each show "N on" while they limit the timeline. Other controls show **counts**: To investigate shows events marked Malicious or Suspicious and events with a pending suggestion; Hosts shows hosts needing review; Rules shows rule errors, only when there are any. |
| Fit case | The Timeline toolbar button that shows the whole case, less far-off strays: it leaves out the earliest and latest 0.05% of events unless they lie within a tenth of the span of the rest. Its hover text, and the status line while the fitted range is in view, say how many lie outside and when. Strays can be leads, such as a timestomped file or a skewed clock. |
| Status line | The text at the end of the Case panel. It reports the last action and the server's time for it, such as "Marked 2 events Suspicious · 25 ms" or "Window moved · 31 ms" after a pan or zoom, then "Sources filtered" or the View while a filter is on. While Fit case's range is in view, "Outside this view" says how many events the filter shows lie before and after the window drawn, and from and to when. The action stays through redraws of the same window; it does not count events (the state line does). |
| Hosts panel | The table under the Case panel, opened by Hosts in the Case menu. For each host: the role with where it came from and a Confirm button while it is a guess, what needs review, names and IPs (each removable, conflicts highlighted), the OS, and the clock offset, with the **clock check** beneath it. Above the table, a **split notice** for each host whose event logs record several computers, with **Split HOST by recorded computer…**, which opens the split's preview, and **Keep HOST as one host**; a line for each host kept as one host, which still offers the split; and a line for each split host with **Undo split**. |
| Timeline panel | The Timeline toolbar and the state line, then the time axis, the lane labels, and the timeline canvas, scrolling together vertically |
| Time axis | The UTC ruler above the lanes, always first. The toolbar's "+ zone" button adds zone axes under it. |
| Zone axis | A ruler under the time axis that labels the same instants in another zone's local time, so a tick reads straight down from UTC. Its label gives the zone's abbreviation and UTC offset for the window (both, if daylight saving changes inside it), and an × removes it. Added from the hosts' own zones or any IANA zone; at most six; saved with the case as the `time_zones` case setting. |
| Lane labels | The nested list of lane names and counts at the left of the Timeline panel. A dashed **guessed** marker on a host label, or "N guessed" on a role label, means a role is still a guess. A **clock flag**, such as "clock +1 h", marks a host whose clock disagrees with a capture's, with an asterisk when the host logged clock changes; its hover text gives the exact skew, the measurement, and the changes. The **lane label divider** on their right edge shows its own grip, a short vertical handle, on hover and focus, and resizes them: drag it, double-click to fit the longest label (up to half the panel), or use the arrow keys. This browser remembers the width; the labels narrow while the Sources or View panel needs the room. |
| Timeline canvas | The drawing area to the right of the lane labels |
| Sources panel | The panel left of the Timeline panel, opened by the Sources button; it decides what the timeline can show, by evidence type, host, file, and channel. A check means shown on the timeline, and counts read "shown of all" when part is hidden; both come from the server's count of what the current filter shows, so they are true whichever rule hid the events. It holds the active filters as chips (each removable, plus Clear all), **Evidence types, across all hosts** (each type with its tool, version, and runs), and **Hosts and files**, a tree of host, evidence type, and file with a search box. A file whose events have several channels opens to them, such as a capture's Suricata record types (flow, dns, http, alert, and the rest) or an Autoruns CSV's categories. A more specific choice overrides a broader one, so a hidden host can still show one of its files. A click shows all of an item when it can, and otherwise hides it. Right-click an item for the context menu. |
| Divider | The bar between the Timeline panel and the Details panel, with a **grip**, a short rounded handle in its middle that shows it can be dragged and turns to the accent color on hover and focus. Drag it to resize the Details panel, or focus it and use the arrow keys (Shift for bigger steps). Double-click resets it. This browser remembers the size. |
| Details panel | The lower area, which shows one page at a time. It opens at two-thirds of the panel area and follows it until the analyst sets a height. It has a **Details band** (below) over one scroller, so the band never moves. |
| Details band | The warm band at the top of the Details panel, 26 px, outside the scroller. It holds the name Details, what the page shows (such as "Search: C137.local"), the Back link when there is one, and the **trail**. The Hosts panel opens with the same band, named Hosts. |
| Trail | The pivot trail in the Details band: the event the analyst started from, each pivot taken, and each event opened from a pivot's list. It shows once there are two steps, on every page. The step the panel shows is not a link. Going back to an earlier step keeps the later ones, **dimmed**: still blue links, lighter, with a dashed underline of 6 px dashes and 4 px gaps. Save trail as a note journals it. A search typed in the box starts a new trail. |
| Dimmed step | A trail step after the one on screen: a step the analyst went back from. It is still a link, in the link color but lighter and with a dashed underline (6 px dashes, 4 px gaps), and it stays until a new pivot or another event from a list replaces it. A pivot or event the trail has next only moves forward to it. |
| Save trail as a note | The trail band's button, which names its target: "Save trail as a note on the 4624 (start)". It journals every step, dimmed ones included, as an ordinary note on the event the trail started from, not necessarily the one on screen; its hover says which. The status line reports "Saved the trail as note #N on the 4624". |
| Show reasons | The tick in the Next pivots heading. On, each pivot row shows its reason, its flags, and its caveat; off, they fold and the row keeps the words "Broad" and "caveat" beside its title. Remembered in this browser. A row's arrow (▾ open, ▸ folded) opens or folds that row alone, for the event on screen. A caveat begins "Caveat:". |
| Provenance strip | The Event page's one line under the header: the tool and run that read the event, the evidence file and record, the file's SHA-256 against the intake manifest, and the build showing it. A part that does not fit is cut with an ellipsis and has its whole text in its hover. The hash check is never cut. |
| Record and source | The fold on the Event page's facts that holds the record's own fields (time meaning, event ID, provider, channel, record ID, rule, computer name recorded, host folder) and where it came from (tool, run, artifact, evidence file and its hash, source record, event UID), with each field's Add to view and Add to search. Closed until opened. This browser remembers whether it is open. A search highlight inside it opens it for that page. |
| Event page | The Details panel's page for one event, in three tiers: the **header** (what the analyst reads at once), the **provenance strip** (where the event came from), and two columns. The facts column on the left holds the field groups, then the folds Record and source and Raw fields, then Notes and History. The shaded work column on the right holds the next pivots and the list a pivot opened. |
| Header | The top of the Event page, in two rows with a third only when something needs saying. Its left edge takes the current mark's color. It stays in view while the two columns scroll. When the header and the provenance strip leave the columns less than 160 px of the Details panel, the panel scrolls to them, the header with it. Between 960 and 1,150 px its right cells drop under the left ones. |
| Event zone | The header's left cells: the identity (time, host, the clock chip, which reads "Clock adjusted +N s" or, on a host aligned to the capture, "Aligned -N s" with the clock note in its hover, and the kind of event) and, under it, the most severe Hayabusa hit, a "+N" link for the rest, and a one-line summary of who acted and on what. The time's hover has the time as recorded, which a clock offset doesn't move, and the host's own local time when its zone is known. A host whose clock was right needs no offset and gets no chip, so its clock note is the time's hover. A time the host's clock didn't write, such as an Autoruns PE link time, has a "Host offset +N s" chip instead, and no clock note or host local time. |
| Verdict zone | The header's right cells. Its first row leads with what the event needs: "Decision needed" with Accept and Reject for a pending suggestion, or once marked, the mark and who set it and when. Its second row is the other marks, a note box, + Tag, and the suggested tags toggle. A note typed in it goes with Accept as well as with the mark buttons. With several events selected, it says "Verdict for N selected events" and marks them all. |
| Field groups | The Event page's labeled lists: Account and logon; Process, file, and registry; and the artifact's own group (Event data for EVTX, Hayabusa details, MFT entry, Prefetch, Shortcut (LNK), Registry value, ShellBag, Amcache, Jump list, SRUM, Recycle Bin, or Autoruns entry). Other artifacts' own fields, such as an import's, are under Raw fields. Empty fields are left out. Click a value to copy it. |
| Raw fields | The fold at the end of the Event page's facts: every event column and extra field, with Copy as JSON. Closed until opened. This browser remembers whether it is open. |
| Pile list | The list shown in the Details panel when a click lands on several stacked events, for picking one. On screen: "N events under the cursor". A plain click on the stack starts a new selection; a shift-click keeps the selection, and a shift-click on a listed event adds it. |
| Related list | The list under Find related on the Event page after a pivot, such as "190 events with the same host and logon ID". A click anywhere on a row but its tick box opens that event, as on the Search page. It stays while you mark events from it, and the note box beside its mark buttons goes with the mark. After Same IP at either end it has an End column for which end of the connection held the address. A cut list has a **reach line** under its heading. |
| Breakdown entry | One source in a pivot row's breakdown, such as "7036 2": the source's name and its event count, a link that opens the row's list narrowed to that source with the count as its total, and the heading then ends ", only 7036". A source no search can ask for (an empty logon type) is plain text, and "+N more sources" is text. |
| Offset | How far in time a listed event is from the event on screen, in the list's Offset column, on a dashed window link, and in a reach line: "+4 s", "+1 min 2 s", "-2 h 21 min", "-9 y 159 d", and "+412 ms" under a second. A gap of a minute or more is in full text, a smaller one muted, and the hover gives the exact seconds. |
| Reach line | The line under a list's heading when the list is cut at 500 and the events have times. A window's says how far the 500 nearest reach against the whole window and where the rest is; another list gives its signed reach, such as "These 500 reach -2 h 21 min to +2 h 9 min around this event." |
| Outside end | The end of an IDS alert's connection that is not a collected host's address. It is a ranked Same IP row of its own, after the internal end, with a count. An alert's source isn't always the attacker. |
| To investigate page | The worklist: two sections with a progress meter each. **Marked events to follow up** lists the Malicious and Suspicious events under a sticky head (Done, Mark, Time, Host, Event, Still unreviewed around it), each with its mark's note and, beside it, its top three pivots counted as unreviewed events; a count in blue opens that pivot's list kept to unreviewed events, and 0 is text. **Pending suggestions, by rule** lists each source with pending suggestions: its name (a link to its Suggestions page), why it fired, its progress, Review one by one, Accept all, and Reject all. |
| Followed up | Your own tick on a marked event in To investigate's Done column, journaled as a `followup` entry with who and when; the row reads "Followed up 22:40 by cody" with the full time in its hover, and the section's meter counts it ("2 of 5 followed up"). It stays when the mark changes later, and the row then says so. Untick it to clear it. Never a fifth badge letter. |
| Still unreviewed around it | To investigate's last column: for each marked event, the first three countable pivots of its kind's ranking, each counted as events with no mark after the page draws ("Same logon session 17", "Same host within ±300 s 205"). A pending suggestion is not a mark, so such an event counts. The hover names the pivot's reason. A search row and Same logon session on a system session are never among them. |
| Unreviewed only | A pivot's list kept to events with no mark, which a To investigate count opens (`unreviewed=1` on `/api/related`): its heading and trail step end ", unreviewed only", and its total is the count. A mark made from it redraws it still narrowed. |
| Review one by one | The lead button of a pending rule on To investigate: it opens the rule's first pending event on the Event page with a **review bar** ("hayabusa: 3 of 58": Accept as the suggested mark, Reject with its note, Next, Stop reviewing) and walks the set the page counted, in time order. The keys A, R, and N accept, reject, and move on from anywhere on the page but a field. |
| Confirm block | The question before a group action: Accept all, Reject all, and a group's Accept N or Reject N always ask; a mark or a tag of more than 25 hand-picked events asks. It names the action, the mark, the source or group, the count the page counted when it loaded and when, what that covers, the first few events, and how many arrived after the page loaded and are not included; the lead button repeats the number, "Show all N first" lists the whole group, and Escape or Cancel changes nothing. The page then sends the exact events it counted; the server skips any no longer pending, says how many, and the entry records `confirmed {count, skipped}`. |
| Suggestions page | One suggestion source's pending events, in groups: Hayabusa by rule title, and Suricata and imported fast alerts by signature, most severe first; rules by account. Group by also offers host and event ID. Accept and Reject work per event (at once), per group (all of a group's events, even beyond the 200 listed), or for the whole source; the group and source buttons ask first with the confirm block, which names the events counted when the page loaded. Accepting marks, so it takes at most 200,000 events at once, as a mark does; past that, accept a group at a time, and group the suggestions another way when one group holds more. The listed events are highlighted on the timeline. |
| Rules page | The suggestion rules, their match and pending counts, and the rule editor |
| Findings page | The page the path's Findings, or Export in the Case menu, opens: the findings on the left and the report, the exports, and **Written from this case** on the right, one column on a narrow panel. Each finding is a card with its **severity** chip, number and title, narrative, ATT&CK line, event chips, and **What this does not prove**; New finding, Edit, Unlink, Retire, and Restore; "N marked events are in no finding yet" with Show them. The right column holds the **Report** (its outline, the **Summary**, Write report, and Preview), the **export cards**, and "Apply the current Sources and View (N) to the report", off by default. When on, the report's opening states the filter. The window export always applies the filters that are on, and its file name says `filtered`. |
| Report | The Markdown file Write report (Markdown) on the Findings page, or `glessner findings`, writes: seven sections, Summary, Findings, Timeline of marked events, Indicators, Hosts and clocks, Evidence and integrity, and Method. The Summary and the findings are the analyst's words; the app adds the rest from the case. The Method table gives each run's rule or map set and, below it, the SHA-256 of the files each tool ran with, and an event of found output cites the output file's hash, as its Event page does. Evidence and integrity says whether `manifest.jsonl` matches its record in the journal, grew past it, differs from it, or has none, and names a missing manifest the journal records. It re-hashes the evidence when written and prints the journal's head, and its file entry is of kind `report`. |
| Summary (of the report) | The report's first section, a paragraph the analyst writes on the Findings page and saves, journaled as the case setting `report_summary` ("Wrote the report summary: ..." in the trail). Empty, the report says no summary has been written. |
| Preview (of the report) | The report's text shown on the Findings page as Write report would write it now, with no file, no journal entry, and no evidence re-hash, which the text says. |
| Export card | One of the four exports on the Findings page, each naming its scope and contents before the click: **Marked events** (the whole case; all marked, or Malicious and Suspicious only), **Events in the window** (the window shown, with the events in it, and the filters that are on), **Indicators** (the Malicious marks), and **Audit trail** (the whole journal). |
| Indicators | The values parsed from the events marked Malicious: addresses, domains, hashes, accounts, file paths, services, and tasks, each with how many marked events carry it and when it was first and last seen. A file in the Windows folder's own files, or below System32, SysWOW64, or Sysnative, carries a note that it may be a system tool the attacker used, so check it before you block it. Read from parsed fields only, never from free text; the case's own hosts' addresses, addresses that name no host (loopback, broadcast, multicast, link-local), and a logon's process are left out. The report's section 4, and the `indicators.csv` export (file kind `indicators`). |
| Written from this case | The table under the exports: every file the case wrote (`state.files`, newest first) with when, the file, its rows, and its SHA-256 short, the whole in the hover. Each file is hashed when written and recorded in the journal, so a copy handed on can be checked against the case. |
| Finding | A short conclusion the analyst writes and the journal records: a title, a **severity**, a narrative, ATT&CK techniques picked in the **ATT&CK field**, and the events that support it, linked by their IDs. The app never writes a finding or its words. A finding is named by the number of its add; retiring it folds it away with its reason, and Restore brings it back. Each linked event shows the mark it has now. |
| ATT&CK field | The finding form's techniques: a box that lists Enterprise ATT&CK's current techniques and sub-techniques as you type an ID, with or without its T, or words of a name, and the picked ones as chips with × to remove each. Only a listed technique can be picked, and the server takes no other. The list is MITRE's Enterprise ATT&CK v20.0, shipped with the app. An ID on a finding that isn't on the list, which only a finding saved by an older build can hold, is **flagged**: "revoked; now T1059.001" for one MITRE revoked, "not in ATT&CK v20.0" otherwise, on the card, in the report, and as a dashed chip in the form, which an edit of the techniques must remove. |
| Severity | A finding's weight in words, one of Critical, High, Medium, Low, and Informational, shown as a worded chip on the Hayabusa level chips' pattern and never as a mark's letter or fill. |
| What this does not prove | The caveat: what a kind of record does not show, in a sourced text fixed per artifact and event type (Prefetch, an Amcache entry, an AppCompatCache entry, a shortcut or jump list, the logons 4624 and 4625, an Autoruns entry, a Suricata alert, a 7045). The Event page shows the record's beside the record, with Show less; a finding's card shows those of its events' types. A kind with no text in the table shows none. |
| Add to a finding | The Event page's **+ Finding** button, beside + Tag in the header's second row, which opens a picker in the third row: the open findings or New finding, and a bordered button naming its target ("Add the 4624 on DC01", "Add the 3 selected events"). "In the finding: 1. ..." shows there when the event is in one. More than 25 events ask first. |
| Tooltip | The box that follows the mouse over an event tick, density bar, or arrow. An event's first line is the state, the kind, and the host ("Suspicious · 7036 Service state · DC01"), with no badge, since the state is a word; the time and message are under it |
| Quick-action menu | The right-click menu on an event tick or logon arrow: marks, suggestion decisions, and the pivots the Event page offers for that event, in its kind's order and without counts, Same IP at either end once for each address a row takes, then the pivots the event can't take, disabled, plus "Zoom to ±N s around it" (N is the case's time window). Its **menu head** says which event it is for ("Menu for this event", or "Menu for N selected events" when the click is inside a selection, since the marks then act on all of them), with the event's badge and its kind, host, and time, its message, and, when other events are drawn within 3 px of the pointer, "2 other events within 3 px: show all 3 here", a link to the pile list. The menu opens with nothing selected: the first arrow down takes the first item and the first arrow up the last, and Enter or Space before that does nothing. "Customize this menu…" picks the actions it shows, saved in this browser. |
| Context menu | The right-click menu on a lane label or a Sources panel item: Show only, Hide, and checkboxes for the evidence types and the top event log channels inside the item, with "shown of all" counts. A checkbox there acts within that item only, such as Security on DC01, and the menu stays open and updates for several changes. Host and role labels add the role actions: confirm or change a role, or open a host in the Hosts panel. |

## On the timeline canvas

| Name | What it is |
|---|---|
| Lane | One row of the timeline. A **leaf lane** holds events, such as Unreviewed > Workstations > DESKTOP. |
| Lane group | A parent row that nests lanes, such as Unreviewed or Domain controllers. Click its label to collapse it, and the collapsed row then shows its lanes' events. |
| Lane keys | The fields that build the lanes, in order: mark, role, host, user, artifact, or tactic. The Lanes selector offers seven presets of them. A user lane holds every letter case of an account's name, labeled with the case's most common spelling. |
| Outside lane | A lane under "Sources outside the case" for a logon source that is not a collected host, such as `194.61.24.102` |
| Density bar | A shaded block in density mode, counting the events in one time bucket of one lane. A red top edge means a Hayabusa hit at medium level or above. A click zooms in around it until the bar fills a quarter of the timeline width. |
| Event tick | One event's mark in event mode. Filled when marked or unreviewed, hollow when only suggested, outlined red for a Hayabusa hit at medium level or above. |
| Density mode, event mode | The two ways the canvas draws. It switches to event mode when the window holds no more than the event threshold (50,000 events by default). |
| Logon arrow | A solid arrow from a logon's source host lane to the host that recorded it. Dashed when the source is an outside lane. Grouped arrows show a count. Zoomed out (density mode), a click on a grouped arrow zooms in like a density bar, and a click on a single arrow selects its logon and zooms in to it. Zoomed in, a click selects the logon in place. Where an arrow crosses an event tick, a click selects the tick. |
| Window link | A dashed curve from the focused event to a neighbor on the same host, labeled with the gap in the offset's units, after the "Same host within ±N s" pivot |
| Selection, focus | The selected events take the next mark. The focus is the one event shown on the Event page. Shift-click adds to the selection. A right-click on an event outside the selection selects it; inside the selection, the selection stays, so the quick-action menu marks all of it. |
| Click, drag | A press that moves less than 4 px is a click; one that moves farther is a drag, which pans. The rule for clicks follows the zoom level. Zoomed out (density mode), every click zooms in. Zoomed in (event mode), a click on a tick or arrow selects it and the window stays still, so shift-click and right-click keep their target under the cursor. |
| Canvas cursor | An open hand over empty canvas (drag to pan), an arrow over something a click selects, and a magnifier over something a click zooms into |
| Zoom animation | The window's half-second move when a click zooms in, when Fit case runs, or when a list jumps to an event. The time under the cursor stays put while the scale changes. The wheel or a drag stops it. The operating system's reduced-motion setting turns it off. |
| Wheel zoom | Scrolling over the timeline zooms around the time under the cursor by how far the wheel or touchpad moved: a mouse wheel's notch zooms by √2, a touchpad's small steps by little, and one wheel event by at most about 2.8 times. |
| Window | The visible span of time, from its start to its end in UTC. Not a screen area. |

## Case and data

| Name | What it is |
|---|---|
| Case | One investigation: a case folder holding `case.yaml`, the manifest, runs, the events database, the journal, and exports |
| Evidence folder | The collection the case examines, one folder per host. Never written to. |
| Manifest | `manifest.jsonl`: every evidence file's path, size, SHA-256, artifact type, and how it was identified, written at intake. Add new evidence appends lines and never changes earlier ones. From case format 4 the journal records its SHA-256, size, and non-blank line count at each intake and Add new evidence (`manifest_recorded`). `verify`, `close`, and the report compare the file with the newest record at or before the head they check against. The answer is one of four: matches; grew past it (only whole lines in Add new evidence's own form, for paths not listed yet, follow the recorded bytes, as a stop between its write and its record leaves); differs; or no record. At a full check, a path the manifest lists twice is a problem of that file. |
| Intake | Hashing and identifying every evidence file. Junctions, symbolic links, and other folder reparse points aren't followed; each is listed with its target. |
| Tools folder | The folder the case names for its tools, which detection searches, with PATH, for each registry tool's executable. It can't hold or sit in the evidence or case folder, or be a network path, since the app runs what it finds there. |
| Case copy | A new case on the same evidence with the source case's intake and tool runs and a new journal, whose first entry names the source, for a clean round such as a blind review or a trial tester's own case. Made with `copy-case`; its `case.yaml` says what it was copied from. Its events keep the source's evidence paths and IDs, except that a copy of a format 1 case is upgraded first, so its journal starts with that `case_upgrade` entry and its events take format 2's IDs. A copy of a format 1 or 2 case has the seal before `case_created`, and every copy has the entries of the steps after the seal, such as format 4's, after `case_created`. The copy holds the source's `manifest.jsonl` byte for byte, and its journal carries, in a record of its own (via copy), the record that the source's own `verify` counts, so the copy's `verify` compares the file with the same record. When the source couldn't vouch for that record, the copy's record also says why: the source's journal has a break, no head of it was recorded on this computer, or its first record came with Add new evidence. `verify`, `close`, the report, the Case overview's Integrity, the case state in the Case panel, and the audit trail repeat the reason. The case state reads it from the journal's first record, so it shows as soon as the copy opens, before the copy's own first full re-hash. A break or a head not recorded here is a warning in Integrity and in the case state. Add new evidence is a note, which the case state gives only in its hover. A source whose journal records no manifest, or whose records all come after the head recorded on this computer, gets no record in its copy, since its own `verify` counts none. A source whose recorded head is no line of its journal also counts none in its own `verify`. Its copy carries the source's newest record, with the break reason, so the copy still warns. |
| Add new evidence | Hashing and identifying files copied into the evidence folder after intake, and adding them to the manifest without changing its earlier lines. The Import page's button, or `intake --add`. From case format 4 it records `manifest.jsonl` after writing it. It also records `manifest.jsonl` when it only grew past its record, even with nothing new to add, so a retry after a stop clears the mismatch. Before hashing anything, it refuses a `manifest.jsonl` that differs from its record or is missing while the journal records it. |
| Import | Reading a text log that no tool reads, such as a firewall log or a SIEM export, into events by a mapping. Each import is a run with tool `import`. |
| Mapping | How an import turns a file's records into events: the format, the time field and its zone, which fields fill the event's own columns, the host lane, and a message template. **Ready-made** mappings cover Windows Firewall, IIS, FortiGate, SonicWall, Apache and NGINX access logs, Apache error logs, syslog, Cisco ASA, Snort and Suricata fast alerts, Zeek's logs, and lines that start with a date and time (`imports.PRESETS`); **saved** mappings are the analyst's, in the case's `mappings` folder. |
| Layout | For log lines, which known layout a file's lines follow, such as Syslog or Cisco ASA (`line_logs.py`). Intake recognizes it from the first lines; the Import page's Layout menu changes it. |
| Import page | The page Import in the Case menu opens in the Details panel: the files to import on the left, with Add new evidence, and under them, Loaded as found output, any Autoruns CSV the Tools page loaded, which can't be imported again; the chosen file's mapping, first records, problems, and first events on the right; and Import, which needs every problem settled, such as a zone for times written without one |
| Host | A collected machine, named by its top-level evidence folder, such as DC01, or after a **split by recorded computer**, one of the computers whose event logs a host folder held |
| Origin host | The host folder an event was loaded under (`origin_host`), which its ID hashes. It differs from the event's host only after a split by recorded computer. The Event page shows it as Host folder, and the timeline export as `labels.collection_host`. |
| Split by recorded computer | Moving a host's event log events, and Hayabusa's hits on them, to one new host per computer the events record, for a host folder of logs from many machines or a log collector's forwarded events. Offered by the Hosts panel's split notice, with a preview. The split is a journal entry; event IDs don't change, so marks, notes, and tags stay with their events; **Undo split** puts the host back. Evidence that isn't an event log stays on the host. **Keep as one host** journals that the computers belong together; the split stays on offer from the host's line. |
| Host identity | The names, IPs, role, OS, time zone, and clock offset tied to a host |
| Host time zone | The zone in a host's SYSTEM hive (`TimeZoneInformation`: TimeZoneKeyName, Bias, and the daylight saving rules), mapped to an IANA zone through the ICU that ships with Windows. Without a match, or with daylight saving turned off on the host, it is the registry's fixed Bias, and the zone axis says so. Different from the **clock offset**, which corrects a wrong clock. |
| Role | A host's asset type: Domain controllers, Servers, Workstations, or Network devices. Either **guessed** from the evidence, with a reason, or set by the analyst. A **confirmed** role is a guess the analyst checked; the journal entry says `confirmed`. The guess uses, in order: events only from FortiGate, SonicWall, or Cisco ASA logs or a network sensor (Network devices), the SYSTEM hive's ProductType (LanmanNT, ServerNT, WinNT), Kerberos ticket requests (event 4768, logged only by domain controllers), a product name that names a server, the host's names, and any other product name (Workstations). |
| Hosts needing review | Hosts whose role is still a guess, with a name or IP that another host also claims, with an IP whose logons name another machine, with a clock that looks off from the capture, or whose event logs record several computers. A claimed-twice name or IP links to no host until the analyst settles it. A host gets a note for each of its IPs whose network logons (4624 type 3) record another machine's workstation name, as after a stale DHCP lease. The note counts those logons and names the machines, such as "3 logons from 192.168.1.23 name ATTACKER-PC, not this host". The logon links stay as they are. |
| Tool | An external forensic program, such as EvtxECmd or Hayabusa |
| Tool registry | The `registry/` folder of tool YAML files. Always say "tool registry" so it isn't confused with the Windows registry. |
| Run | One execution of one tool against one host's evidence, or one file of it for a tool that reads a file at a time, with a **run record** (`run.json`). An import of one file and a load of found output are runs too. From case format 4, the run record also holds the label of the rule or map set the run used (`rules`), the SHA-256 of the tool's files (`tool_files`), and the count of rows or lines a parser made no event of (`rows_skipped`). |
| Tool files | The files in a tool's own folder that a run names, recorded in its run record with their SHA-256 (`tool_files`): the executable and the `.dll` of the same name, the files its command line names there, its rules block's version file, and the files and folders its registry file lists, such as Hayabusa's `rules` and `config`, the `Maps` of EvtxECmd and SQLECmd, and RECmd's `Plugins`. A folder is recorded under its path and a `/`, with the SHA-256 of its listing: one `<sha256>  <path>` line for each file in it, as `sha256sum` prints them, with forward slashes in the paths, sorted by code point, leaving out `.git` and skipping links. To reproduce a folder's hash in Git Bash, work inside the folder. List its files with `find . -type f -not -path '*/.git/*' -not -name .git -printf '%P\n'`, sort those paths with `LC_ALL=C sort`, run `xargs -d '\n' sha256sum -t` on the sorted paths, and hash that output with `sha256sum`. The `-t` is needed because Git for Windows' `sha256sum` marks lines as binary otherwise. Sorting the `sha256sum` lines instead of the paths gives a different hash, since each line starts with the file's hash. A builtin tool, an import, found output, and a run made before case format 4 record none. |
| Start page | What the app shows with no case open, and what **Cases** in the Case menu opens: recent cases, each with its count of timeline events, with **Open** and **Copy**, a box to open any case folder, and **New case**, which checks the chosen folders, takes the evidence in with progress, and opens the case on its Tools page. New case and Copy each take an **Analyst**, filled in with the Windows user name, whom the case's journal credits with every action. The tools folder's check names the file each tool would run. When top-level folders of the evidence each hold the same host's folder, as copies of one collection do, a warning under the evidence check names them and one host; the case can still be created. A quiet line at its foot names the **build**. |
| Tools page | The page Tools in the Case menu opens in the Details panel: the latest runs that failed or loaded nothing, which the Case overview's Gaps link to; each registry tool's version, what it would read in this case, whether it ran and how many events the case holds from its latest runs, one per host or, for a tool that runs once per file, one per file (Hayabusa's as hits), with the events without a time and the rows skipped, and a line naming the rule or map sets those runs used ("rules not recorded" for a Hayabusa, EvtxECmd, RECmd, or SQLECmd run made before case format 4), and **Run on N hosts** or **Run again**; missing tools with their download pages; evidence no installed tool reads, with the files the Import page offers and the unidentified files, each with intake's reason where it gave one; a line saying it's checking the tools folder while the first answer after a server start takes seconds; and other known tools found in the tools folder; and tools' output already in the evidence, with **Load** |
| Found output | Another tool's output in the evidence folder, such as the CSVs a KAPE run writes, recognized by its header and loaded with the tool's own parser instead of running the tool. Raw evidence comes first: output for a host whose raw files an installed tool reads stays unloaded unless the analyst picks **Load anyway**. Its events carry the tool version `found output`. Zeek's logs load through the import, with the ready-made `zeek` mapping; Suricata's EVE JSON loads by the parser of the app's own Suricata runs. Autoruns CSVs load by their own parser, at the UTC offset the host had when Autoruns ran, since Autoruns writes local times at that one offset. |
| Autoruns entry | One autostart entry from a Sysinternals Autoruns CSV (`autorunsc -c`), loaded as found output with artifact `autoruns`: its image as the file path, its launch string as the command line, its location as the registry key where it is one, and the signer, company, description, version, and hashes in its data. Its time is the image's **link time** for a PE file, or the file's last write for another file, such as a script; the time description says which. Neither is when the entry was set. An entry without a time is loaded and counted on the Tools page. |
| Link time | When the linker built a PE image, from its header; Autoruns gives it as an entry's time. Windows 10 links its own binaries with a hash in its place, so their link times fall anywhere from 1902 to 2037. Fit case doesn't let link times set its window, and counts them as strays. |
| Run and load everything ready | The Tools page's top button, and `run --all`: every installed tool that has evidence and hasn't run, then every ready group of found output, in one background job |
| Working copies | Copies of a run's inputs in its run folder, for a tool that writes beside what it reads, such as SrumECmd. Each copy is checked against its intake hash first; the run record lists the copies the tool changed. |
| Event | One row of the events table: a timestamp, a host, and what happened, from one artifact through one tool. An event without a timestamp, such as an LNK file without target times, is loaded and counted but stays off the timeline, search, and exports. |
| Looked-up account | The account of an event log event that records the user only by SID, in its System element, such as PowerShell's script block event (4104), or in its own data, such as AppReadiness's User field, named from the same host's 4624s and 4672s, which record the SID with its name (`accounts.py`). The Event page shows **Looked up** under the account: the SID, the name, and how many of which events gave it. The SID stays in the event's data, in `AccountLookedUpSid`, and in the export's `user.id`, and a search for it still finds the event. A SID its host never names stays the account. |
| Artifact | The kind of evidence an event came from: evtx, hayabusa, registry, mft, usnjrnl, prefetch, lnk, shellbags, amcache, jumplist, srum, recycle_bin, browser, notification, timeline, suricata, or autoruns (`parsers.ARTIFACT_NAMES`, with the names the page shows), or an imported log's artifact name, such as windows_firewall, iis, fortinet, sonicwall, web_access, web_error, syslog, cisco_asa, ids_alert, zeek, or text_log |
| Hit | A Hayabusa rule match. It marks the EvtxECmd event it matched instead of getting a lane of its own. |
| Mark | The analyst's verdict on an event: Unreviewed, Authorized, Suspicious, or Malicious |
| Review-state badge | The 16 px letter that leads an event in every list and on the Event page: **U** (hollow ring) unreviewed, **A** (green) authorized, **S** (amber) suspicious, **M** (red) malicious. A pending suggestion reads U. Hover it to read the mark's word, who set it, and when ("Suspicious, marked by cody, 2026-10-17 14:02 UTC"), or for an unreviewed event the suggestion waiting on it. A list's **Mark** heading, which sticks under the panel's head, labels the column. The badge also leads the right-click menu's head. It stands for the state word and never sits beside it, so the menu's Mark items, the Event page's verdict pill, and the tooltip's first line, which spell the state out, carry none. |
| Suggestion | A proposed mark from a **suggestion source**: a suggestion rule, Hayabusa (hits at medium level and above), Suricata (alerts at severity 1 and 2), or `ids_alert` (imported Snort or Suricata fast alerts at priority 1 and 2). The analyst accepts, rejects, or restores it. |
| Suggestion rule | A YAML condition kept in the journal that suggests a mark for matching events. Four are **built in**: machine-accounts-authorized, remote-execution-pipes, print-spooler-pipe, and admin-share-executable-writes; the analyst can change or remove each. |
| Pivot | Finding related events by one kind: same logon session, same account, same source IP, same source IP and port (one network connection, such as a Kerberos ticket request and the network logon made over it), same file, same file name (the name alone, in any folder), same IP at either end, or same host within ±N s, with same service name, workstation, flow, task name, and rule or signature as the Event page offers them. On screen these are the Find related actions, disabled when the event lacks the field a pivot needs, with hover text saying which. Same file matches full paths, so on a file named without its folder, such as a service's cmd.exe, it says the file has no full path to match on. Imports give Same file no path to match, so on an imported event with a full path it says only that Same file can't match on the file. |
| Same IP at either end | The pivot that finds events with one of the event's addresses as their source or their destination. Older Sysmon records the local side of a connection as the source, so on an inbound connection the remote address is the destination: Same source IP from that event finds the host's own address, and from the remote side's 4624 it never reaches the connection. Its row under Find related, "Same IP at either end:", has a button for each distinct address on the event, labeled with it; with none, one disabled **None** button says why. The related list reads "10.0.2.17 at either end: 3 events" and says in its last column, under "10.0.2.17 is the", whether each event had the address as **source**, **destination**, or **both**. Its View and search forms are View at either end and `addr:`. |
| Recorded time, adjusted time | The time an artifact recorded, and that time plus the host's **clock offset**. The canvas, links, and exports use the adjusted time. |
| Clock check | A host's clock measured against a capture's, from events both record: RDP connections, logons, and downloads (`clock.py`). It suggests an offset only when the pairs agree, and lists the clock changes the host logged. Shown in the Hosts panel, as a lane's clock flag, and on the Event page. |
| Clock pair | A host event and the capture record of the same moment, such as a download in the capture and the cache file it wrote on the host. The Event page names an event's pair; **Show the pair** selects it and draws a dashed **pair link** across lanes and time, labeled with what they share and the host's skew. |
| Times switch | "Recorded" or "Aligned to capture" in the Timeline toolbar. Aligning sets each measured host's suggested clock offset as an ordinary journaled offset; Recorded sets back the ones the switch set. "partly aligned" means hosts differ. The state line names the clock too, with Align or Show recorded. Offsets change what the page shows, never the evidence times. |
| Journal | `journal.jsonl`: the append-only record of every analyst action, and of each build that opened the case, the case's only irreplaceable file |
| Hash chain | From case format 3, each journal line's `prev` is the SHA-256 of the line before it as stored, so a change to any earlier line shows as a break. The chain starts at `case_created`, or on an upgraded case at the **seal**, the entry that records the length and SHA-256 of every earlier line. A copy of a case from before format 3 is sealed first, and its `case_created` follows the seal. A chain that checks out is **consistent: each names the one before it**, never "intact": anyone who can write the folder can rewrite the whole chain, so only a head kept outside the case shows that. A **broken** chain opens the case read-only until the analyst continues with the break on record. |
| Head | The SHA-256 of the journal's last chained line, which names everything before it: printed in full by `close`, after each export or report, and by `verify`, and shown short with Copy in the Case overview's Integrity. The app also records it outside the case after every write (the **head record**, in the config folder's `heads\`) and compares it at each open. A head kept outside the case, by the analyst or the app, is what makes the journal tamper-evident: the chain alone can't show the newest lines removed or the whole journal rewritten. A file's record counts only at or before such a head, and so does a record of `manifest.jsonl`. |
| Build | Which version of the app's code is running: the release version from `pyproject.toml`, the commit, and `.dirty` when the package's files differ from it, such as 0.2.0+abc1234. `--version` prints it, the start page's foot shows it, and the report, the audit trail's export, and imported events record it. Opening a case in the app under a build the journal doesn't name last journals "Opened with glessner" and the build. |
| Case format | The number in `case.yaml` that says how the case's database, journal, and manifest are laid out, and by which rules its events take their IDs. A case without one is format 1. Format 2 gives Suricata, SQLECmd, and found Amcache and SRUM events IDs that don't depend on where or in which time zone a tool ran. Format 3 starts the journal's **hash chain**, records where the remaining older tool runs read their files, and adds the events' account key and hash list, for Same account and Same hash. Format 4 adds the run record's `tool_files` and `rows_skipped`, names a run's rule or map set by a label, and has the journal record `manifest.jsonl`'s hash from format 4 on. Once the journal holds such a record, the comparison stays on even when `case_format` in `case.yaml` is set back below 4. A build refuses a case of a newer format than it reads, naming both numbers. It upgrades an older one, with a `case_upgrade` journal entry, when the app opens it for work or a command writes to it; format 1 to 2 reloads the changed events and records each old ID the journal named with its new one, 2 to 3 seals the earlier entries, and 3 to 4 adds one journal entry and raises the number in `case.yaml`, leaving the case's events, runs, and manifest as they are. The exception is found output that an earlier build loaded while `case.yaml` named the evidence through a link: 3 to 4 loads it again, so its events take the IDs a rebuild gives them, and the entry records each old ID the journal named with its new one. A format 3 case whose journal has no chain or has a break stays at format 3 and opens read-only. A setting added to `case.yaml` doesn't change the format; a build refuses a setting it doesn't read, by name. |
| Timeline export | A CSV or JSONL file of events, for Timesketch or Timeline Explorer: the window shown from the Findings page's Events in the window card, or every marked event in the case from its Marked events card, or from `glessner export`. Its columns are ECS names; a network record's row carries its signature as `rule.name` with `rule.id` and `event.severity`, its type as `event.dataset`, and `url.full`, `dns.question.name`, `tls.server.name`, and `client.mac`. Its connection's IDs each have a column: `network.community_id` holds a community ID and nothing else, `network.flow_id` holds Suricata's flow ID, and `zeek.uid` holds Zeek's uid. |
| Filter | What the Timeline panel shows: **Show only** an item, **Hide** items, and **show exceptions** inside hidden ones, each named by field values such as host DC01 and channel Security. The most specific rule wins. Filters change the view, never the case: they are not journaled, and a reload shows every event. Exports ignore them unless the analyst applies them on the Findings page. The Sources panel and the View panel both set the one filter. |
| Audit trail | The page Audit trail, a step of the path after Findings and an entry in the Case menu, opens in the Details panel: every journal entry in plain words, newest first, filtered by action, analyst, text, Corrections only, or one event, with Export (Markdown) for training or review, which lists each event of an entry of several by time, host, event code, and ID. An entry names its one event in quotes, cut at a word or address boundary with "…" past about 100 characters, the whole message and the time in its hover, and a click opens the event; the export writes every name whole. Marks, tags, suggestion decisions, and dismissed tag suggestions have **Undo**; notes have **Retract**; host and rule changes link to their panels. The app's own entries for each build that opened the case are listed under the action **Builds**. |
| Undo | A correction of an accident: a new journal entry that returns each event an earlier entry changed to how it was just before, except events a later entry changed, which keep their later state. The original entry stays, struck through as "Undone by #N". A change of verdict on the evidence uses the normal mark and tag buttons instead. |
| Retract | What happens to a note instead of undo: it stays on record, struck through, with who retracted it and when. |
| History | The Event page's fold of every journal entry for that event, with Open in the audit trail. Its title says how many, "History (4)", or "History (30+)" when the 30 it asks for are all there. Closed until opened. |
| Tag | A label on an event, journaled with who and when like a mark. Three kinds: an ATT&CK **tactic** (Enterprise ATT&CK v20.0's 15, in kill-chain order, kept by ID such as TA0008 so a renamed tactic keeps its tags), an ATT&CK **technique** such as T1021.001, picked from the same Enterprise ATT&CK v20.0 list as the **ATT&CK field**, and the analyst's **own tag**, kept in lower case. An event can carry several. The Event page's verdict zone shows them as chips; × removes one. A technique tag on an ID that isn't on the list, which only an older build could add, is **flagged**, as a finding's is: a dashed chip reading "T9999 (not in ATT&CK v20.0)" or "T1086 (revoked; now T1059.001)", flagged in the View panel and the report too. It can be removed but not added again. |
| Suggested tag | An ATT&CK tactic or technique from a Hayabusa rule that matched the event. The verdict zone says "N suggested tags" with a toggle (`aria-expanded`, closed until opened, which this browser remembers). Opened, the third row of the header shows each as a dashed chip with ✓ at its left end to accept and × at its right end to dismiss, the ends tinted green and red and turning solid under the pointer, plus Accept all and Dismiss all. A dismissed suggestion stays dismissed. Nothing is tagged until the analyst accepts, though the View filter's **Include suggested tags** shows pending ones. |
| Tag picker | The popup that **+ Tag**, the right-click menu's **Tag as...**, and a list's **Tag as...** (**Tag N as...** once rows are ticked) open: the tactics in kill-chain order (a tactic the event has shows ✓, and clicking it removes it), a technique box that lists the ATT&CK field's techniques as you type an ID or words of a name and tags the events with the one you pick (a revoked ID typed names its replacement), and a box for your own tag that offers tags used before. |
| Tactic lanes | The Lanes selector's Tactic > Host preset: one lane group per tagged tactic, in kill-chain order, then Untagged. An event with two tactics sits in both. |
| Search | The box at the start of the Case panel's second row; / focuses it. Words match anywhere in any letter case and all must match; a word or "a phrase" in quotes matches whole words (see **Whole word**); field:value matches a whole value, with * for any text (ip:, port:, user:, code:, host:, process:, path:, and the rest of the View fields, or an event data name such as ProcessName:); **addr:** matches an address at either end, the events ip: or dst: would find, and an event data field named addr is data.addr:; -term excludes. Enter opens the **Search page** in the Details panel: the match count and time span; the **match strip**, bars of match counts over time, each a click from zooming there; **Zoom to the busiest stretch**, the shortest stretch holding half the matches; Fit to all of them; Add this search to view filter; and the first 500 matches to tick and mark, each opening its event from a click anywhere on its row but the tick box, with the search terms highlighted and "in *field*:" with an excerpt where a word was found outside the shown message. The timeline marks every match, up to 20,000. Event pages opened from the results highlight the terms too, until another page opens. Marks and roles aren't search fields; use the View filter and the Lanes selector. A search repeated after events load, and a View holding one, finds the events loaded since. |
| Search help | The page the ? button beside the search box opens: the syntax, worked examples that run with a click (such as Sysmon network connections, `code:3 channel:*sysmon*`), and the fields with an example each |
| Whole word | A word or phrase in quotes in the search box: `"nmap"` finds nmap.exe and NMAP and not WinMaps, x_nmap, or nmap2, where bare `nmap` finds the text anywhere. Letters a to z, digits, and underscore on either side end no match; a side that ends in another character, as in `".dll"`, has no bound; `*` is any text. A field value in quotes still compares as a whole. The **Whole word** tick, first in the Search page's head, quotes every free-text word of the search or takes the quotes off, and is part-checked when only some are quoted. A phrase with spaces stays whole words either way. The highlights follow the bound. |
| rule: (search field) | `rule:"RDP from internet"` or `rule:*mimikatz*`: the events a Hayabusa rule hit, by the rule's title in any letter case, with `*` for any text. | Forgiving search | The line under "Looking for" on a search with a quoted word: "Show what the forgiving search adds" counts, on a click, what the search finds with that word bare. | Also found by name | The box under a search's results that lists the Hayabusa rules whose titles hold the search's first free-text word, up to three, with each rule's level, its event count, the field form (`rule:"..."` with the rest of the query kept) as a link, how many of its events the results already hold, and up to 20 it adds. | Zero-result hint | What a search with no match shows in place of "No event matches.": the text free text searches, the fields it skips (tool, artifact, run, source file, mark, role, tag, and Hayabusa rule titles), the values of those fields that hold the search's words with their event counts, and other forms to try. | Add to search | The action beside a field on the Event page, beside Add to view filter, that puts the field's field:value term in the search box, quoted when needed. Press Enter to run it. |
| Add to view filter | The action beside a field on the Event page, shown on hover or keyboard focus, that pins the field's value in the View. Once the value is active it reads **Remove from view filter**, shown without hovering, and takes the value out. Pivot lists and the Search page carry the same toggle, such as "Add this search to view filter". Every field that can be a value has it, including the event's own data fields by name. Text fields such as account, process, and path match in any letter case, as Windows treats them. On the Source IP and Destination IP rows it is a menu, **Add to view filter ▾**, reading **In view filter ▾** while either of its values is on: **View as source IP** (or destination IP) and **View at either end**, each checked while it is in the View and taken out by a second click, and **Search addr:**, which puts the address's `addr:` term in the search box. |
| View at either end | A View value, `{"addr": ...}`, that shows events with the address as source or destination, chosen from an address row's View menu or a Same IP at either end list. | View panel | Titled **View filter**, matching the Add to view filter actions. The panel left of the Timeline panel, opened by the View button; only one of it and the Sources panel is open at a time. It decides what the timeline shows of what the Sources allow: events with chosen **marks** (Malicious, Suspicious, Suggested, Authorized, Unreviewed), or matching a **pinned value** (a source IP, port, account, or host, or an IP at either end, added with "Add to View" on the Event page or a pivot list). **Presets**: Chain (Malicious and Suspicious, the chain so far), Review (pending suggestions), and All (the View off). **Tactics and tags**: a checkbox per tag in use, and Any tag. Its **Include suggested tags** "(Hayabusa's, not yet accepted)", off by default and after every reload, makes tag values match Hayabusa's pending suggested tags too, never dismissed ones; a tag only Hayabusa suggests can be ticked only then, and its hover text says so. Each section (Marks, Tactics and tags, Values) folds from its heading; a folded one says how many of its values are on, Tactics and tags starts folded while none is on, and this browser remembers the folds. The band's **Close** button shuts the panel, and the View button shows the pressed look while it is open, as the Sources and Legend buttons do. Hidden events still count for pivots, links, and search. |
